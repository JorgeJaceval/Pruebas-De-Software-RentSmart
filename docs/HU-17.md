# HU-17 — Sugerir una descripción con IA (REN-17)

Como propietario, quiero obtener una descripción inicial mediante IA a partir de los datos de mi espacio, para redactar una publicación más fácilmente y adaptarla antes de publicarla. Fuente: `Historias de usuario.pdf`, p. 19; [REN-17](https://rentsmartpsf.atlassian.net/browse/REN-17), CA-01–08. Prioridad media, obligatoria; cubre el requisito "al menos una funcionalidad de IA" (p. 25).

## Proveedor elegido

Usamos la **API de Gemini (Google AI Studio) en su nivel gratuito**, sin cargos ni medios de pago asociados. Elegimos un nivel gratuito para no generar costos en un proyecto académico; su límite de solicitudes es bajo y puede cambiar, por lo que tratamos el límite alcanzado (`429`) como un caso normal con su propio mensaje.

El modelo se configura con `GEMINI_MODEL` y por defecto usa el alias `gemini-flash-lite-latest`, que Google mantiene apuntando a la versión vigente de su modelo liviano. Así evitamos que un nombre de versión fija quede obsoleto. La clave va en `GEMINI_API_KEY`; ambas variables son opcionales.

## Recorrido y decisiones

En **Publicar espacio** y **Editar espacio**, **Sugerir descripción con IA** se habilita cuando nombre, tipo, comuna, capacidad y condiciones son válidos; no hace falta haber publicado. Mientras esperamos, el botón cambia a **Generando sugerencia…**, se informa que puede tardar hasta 15 segundos y no se aceptan solicitudes repetidas. Después de 15 segundos el navegador cancela la espera.

La sugerencia aparece en un recuadro **Generada con IA · revísala antes de usarla**. **Usar sugerencia** la copia al campo Descripción, donde se puede editar; si ya había una descripción escrita, avisamos que se reemplazará. **Descartar sugerencia** no modifica el formulario. Generar nunca publica ni guarda nada: la publicación sigue pasando por las validaciones de HU-03/04.

Si falta la clave, el proveedor tarda, se alcanza su límite o el nuestro por usuario, responde con error o entrega un texto vacío o mayor a 1.000 caracteres, explicamos que no se pudo generar y que se puede escribir manualmente. El formulario conserva todos sus datos. **No presentamos una plantilla estática como si fuera IA.**

## Instrucciones al modelo

El backend envía solo datos textuales: nombre, tipo (en palabras), comuna, capacidad, condiciones y, si es válida, la ubicación referencial. No envía precio, fotos ni datos de la cuenta. La instrucción de sistema pide describir **solo** lo aportado, sin inventar servicios, equipamiento, certificaciones, accesibilidad, precios ni horarios, en 2–4 oraciones y como máximo 600 caracteres. Los datos viajan como JSON delimitado por `<datos>`, con `<` y `>` escapados para que un campo no pueda cerrar el delimitador, y la instrucción indica tratarlos como información, no como órdenes, para reducir instrucciones incrustadas en los campos. Esto reduce pero no garantiza la ausencia de invenciones (fuera de alcance según la p. 19); por eso la revisión humana es obligatoria.

Limpiamos el formato Markdown real (bloques de código, títulos, viñetas, negritas y cursivas), las comillas envolventes y los espacios repetidos, conservando `_`, `#` y `*` dentro del texto (por ejemplo, `3*4` o `Sala_de_reuniones`); solo quitamos comillas que envuelven toda la respuesta. Un texto de más de 4.000 caracteres se rechaza sin limpiarlo. Rechazamos la respuesta si queda fuera de 20–1.000 caracteres (contados como caracteres Unicode, igual en navegador y API), si contiene caracteres de control o texto no codificable, o si el modelo no terminó normalmente (`finishReason` distinto de `STOP`: respuesta cortada o bloqueada).

## Contrato

`POST /api/spaces/description-suggestion` requiere sesión. Cuerpo: `name`, `category`, `commune`, `capacity`, `conditions` y `location_reference` opcional, con los mismos límites de una publicación. Respuesta `200`: `{"suggestion": "..."}`.

| Estado | Caso |
| --- | --- |
| `401` | Sin sesión válida. No se llama al proveedor. |
| `422` | Datos mínimos ausentes o inválidos, o campos extra. No se llama al proveedor. |
| `429` | El proveedor informó límite de uso o cuota, o el usuario superó nuestro límite (5 sugerencias por minuto, con mensaje propio). Sin clave no se cuenta el límite. |
| `502` | Error del proveedor, redirección, respuesta mayor a 64 KiB o no utilizable. |
| `503` | No hay clave configurada. |
| `504` | La llamada completa al proveedor superó 12 segundos (`AI_TIMEOUT_SECONDS`, menor que los 15 del navegador), aunque envíe datos de a poco. |

Los errores devuelven un mensaje propio; nunca reenviamos el cuerpo del proveedor, que podría incluir partes de la solicitud. La clave viaja en la cabecera `x-goog-api-key` desde el backend, no en la URL, y no aparece en respuestas, registros ni en el navegador. El adaptador no sigue redirecciones, para no reenviar la cabecera a otro destino.

La clave se crea gratis en <https://aistudio.google.com/apikey>. No se versiona ni se comparte por chat.

## Evidencia de ejecución real (CA-08)

**Pendiente: requiere una clave real.** Las pruebas automatizadas cubren el endpoint con un proveedor simulado y el adaptador contra un servidor que imita la API, pero no confirman la autenticación con Google ni que el alias de modelo responda. Para registrarlo:

1. Crear una clave gratuita en <https://aistudio.google.com/apikey> y guardarla en `backend/.env` (o en el `.env` de la raíz) como `GEMINI_API_KEY=...`. Ese archivo está ignorado por Git.
2. Desde `backend/`:

   ```bash
   uv run python -m app.ai_evidence --write ../docs/evidencias/REN-17-ia-real-AAAA-MM-DD.md
   ```

   El comando envía un espacio ficticio por el mismo adaptador que usa la API. Registra la fecha, el modelo solicitado, el modelo que respondió (`modelVersion`), la duración, los datos enviados y el texto generado. Nunca imprime la clave y termina con error si falta o si la llamada falla, sin escribir el archivo.
3. Revisar que el texto no agregue servicios ni características ausentes, completar la revisión humana en el archivo y versionarlo con la PR.
4. Probar el recorrido en la interfaz local (`docker compose up`) con la misma clave: pedir la sugerencia, usarla, editarla y descartarla.

## Configuración operativa en producción

La CI y el despliegue no transportan la clave: se configura una vez en el servidor.

1. En el VPS, editar `/opt/rentsmart/shared/.env` (permisos `600`) y agregar `GEMINI_API_KEY=...`. Opcionalmente, `GEMINI_MODEL=...` para fijar otro modelo.
2. Aplicar la variable: ocurre en el siguiente despliegue desde `main`. Para aplicarla sin desplegar, recrear solo la API con la revisión vigente:

   ```bash
   export RELEASE_SHA=SHA_COMPLETO_DE_40_CARACTERES
   docker compose --project-name rentsmart-production --env-file /opt/rentsmart/shared/.env      -f /opt/rentsmart/current/compose.production.yaml up -d --no-deps --no-build backend
   ```

3. Verificar en la aplicación publicada que **Sugerir descripción con IA** devuelve una sugerencia. Sin clave, la aplicación publicada muestra el mensaje de no disponible (CA-06) y el resto de la publicación funciona igual.
4. No incluir la clave en capturas, logs, tickets ni mensajes. Si se expone, revocarla en Google AI Studio y crear otra.

## Fuera de alcance

Analizar fotografías, garantizar que la IA nunca invente, entrenar modelos y recomendar espacios (p. 19). No guardamos las sugerencias. El límite por usuario se cuenta en la memoria de cada proceso: con un solo proceso de API, como hoy en producción, es efectivo; con varios, cada uno contaría por separado.

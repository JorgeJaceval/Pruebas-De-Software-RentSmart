# HU-01 — Registrarse (REN-1)

Como visitante, quiero crear una cuenta con mi nombre, correo y contraseña, para poder publicar espacios y realizar reservas.

Fuente: `Historias de usuario.pdf`, página 7, con los rangos comunes de las páginas 3 y 4. Los mismos seis criterios están en el campo **Test cases** de [REN-1](https://rentsmartpsf.atlassian.net/browse/REN-1). Rama: `feature/REN-1-registro-usuarios`.

## Comportamiento implementado

La sección **Crear cuenta** de la página inicial ofrece los tres campos con sus etiquetas y errores accesibles. El registro llama a `POST /api/auth/register`; una respuesta `201` confirma la creación persistente de la cuenta. No se inicia una sesión automáticamente. El inicio y cierre de sesión se implementan en HU-02, que depende de esta historia.

El nombre se recorta en los extremos y debe tener entre 2 y 80 caracteres. El correo se recorta y convierte a minúsculas antes de validarlo y guardarlo. La contraseña tiene entre 8 y 64 caracteres, conservando espacios y demás caracteres exactamente como fueron ingresados; se almacena únicamente un hash Argon2id con salt generado por pwdlib.

Todos los textos deben poder codificarse como UTF-8. El nombre no admite NUL porque PostgreSQL no puede almacenarlo como texto; la contraseña sí puede incluirlo y se conserva al hashear. El correo se ingresa como dirección simple, sin nombre visible ni delimitadores `< >`. Son decisiones de robustez de la implementación, derivadas de la revisión de entradas inesperadas, no nuevos criterios atribuidos al PDF.

La API acepta únicamente `name`, `email` y `password`. El identificador UUID se genera en el servidor y `is_admin` siempre es `false` para el registro público. La misma cuenta puede participar como propietaria y arrendataria: no se exige elegir un rol al registrarse.

## Estrategia y comandos

- **Jest + React Testing Library:** prueba componentes en jsdom con `fetch` simulado, cambios de campos mediante `fireEvent` y acciones mediante `userEvent`. Verifica validaciones, éxito, errores por campo, reintentos y bloqueo durante el envío.
- **Pytest + TestClient:** valida el contrato de API y los casos inválidos sobre SQLite en memoria, con sesiones SQLModel sustituidas mediante `dependency_overrides`.
- **PostgreSQL real:** aplica Alembic en un esquema temporal independiente por prueba. Comprueba persistencia, normalización, restricciones y una carrera real de registro. Al finalizar elimina únicamente el esquema generado para esa prueba.

Desde `frontend`:

```bash
npm run test:ci
npm run build
```

Con PostgreSQL disponible, desde `backend`:

```bash
uv sync --frozen
uv run alembic upgrade head
uv run pytest -q
uv run alembic check
```

La base de pruebas debe permitir crear esquemas. El usuario de desarrollo configurado por Compose tiene ese permiso. Para los casos aislados que no requieren PostgreSQL, usa `uv run pytest -m "not postgres" -q`.

No se agregan ni ejecutan E2E en esta historia: corresponden a la entrega 3.

## API y manejo de errores

El éxito devuelve exclusivamente `id`, `name` y `email`. Los errores usan `{ "detail": "mensaje", "errors": { "campo": "mensaje" } }`, con códigos `409` para correo duplicado, `422` para validaciones y `503` para indisponibilidad de persistencia. La API no devuelve los valores de entrada, la contraseña, el hash ni los detalles internos de la conexión.

Los errores de validación de FastAPI tienen un handler que publica mensajes por campo sin incluir los valores enviados. La configuración no activa registros de cuerpos de solicitud ni echo SQL. Las evidencias del formulario se capturan vacío o después del éxito para no mostrar contraseñas.

La migración `0001_create_users` establece la restricción `uq_users_email` y las comprobaciones de correo normalizado y longitud de nombre. El conflicto se resuelve con la restricción de PostgreSQL y rollback de la sesión que pierde la carrera; no depende de una comprobación previa en la interfaz.

La respuesta pública se construye antes del commit y solo se devuelve después de que la cuenta quedó guardada. Esto evita depender de una consulta posterior que pudiera fallar y comunicar falsamente que el registro no se realizó.

# HU-16 — Pagar mediante un simulador (REN-16)

Como arrendatario, quiero realizar un pago simulado de mi reserva para completar el recorrido de arriendo y conocer si quedó confirmada para su uso.

Fuente: [REN-16](https://rentsmartpsf.atlassian.net/browse/REN-16). Desarrollamos API, interfaz y pruebas en REN-79, REN-80 y REN-82. Reutilizamos reservas y contrato económico de HU-12 y lecturas privadas de HU-13.

## Comportamiento

Desde **Mis reservas** o el resumen de una reserva elegible, **Pagar reserva** abre `#pago/{id}`. Mostramos espacio, intervalo, total contratado, plazo y estados actuales, con un aviso explícito de simulación sin dinero real ni datos de tarjeta. El usuario elige aprobar o rechazar y confirma. Bloqueamos el doble envío; mostramos el resultado después de la confirmación de la API.

Un rechazo conserva la reserva pendiente y permite un nuevo intento mientras siga vigente. **Actualizar reserva** consulta la persistencia si hubo un fallo o un resultado incierto. Tras aprobar, el resumen y Mis reservas presentan referencia, importe y fecha del pago; las lecturas antiguas sin esa información siguen disponibles. Conservamos la ruta al iniciar sesión y descartamos respuestas tardías al cerrar sesión, navegar o vencer el acceso.

## API y persistencia

`POST /api/reservations/{id}/payment` recibe `{result: "approved"}` o `{result: "rejected"}` y devuelve `ReservationRead` con el resultado confirmado. Rechazamos campos adicionales. La referencia es el UUID estable de `Payment.id`; `amount` y `processed_at` registran el importe contratado y el último resultado procesado. Una aprobación posterior al rechazo conserva referencia y registra la fecha de aprobación; futuros reintentos conservan ese resultado.

Solo opera el arrendatario, incluso frente al propietario o un administrador. Reserva ajena e inexistente reciben el mismo `404`; sin sesión respondemos `401`, datos inválidos `422`, estado/plazo no permitido `409` y fallo SQL `503` controlado. Las respuestas privadas usan `Cache-Control: no-store`.

Bloqueamos en orden espacio → reserva → pago y leemos la hora después de esperar. Una pendiente vigente admite aprobación o rechazo; en el instante de vencimiento o inicio ya no puede pagarse. Una reserva pagada con pago aprobado devuelve el mismo resultado sin nuevas escrituras, aunque el nuevo intento solicite rechazo. Canceladas, expiradas y finalizadas no se reabren. Un cambio de precio, desactivación o retiro no impide pagar un contrato aún válido.

Pago y reserva se guardan en la misma transacción; construimos la respuesta y solo la devolvemos después de confirmar el commit. Un fallo hace rollback. Las futuras escrituras de cancelación deben mantener el orden de bloqueos y registrar conjuntamente un reembolso cuando corresponda.

`0006_payment_simulation` agrega columnas opcionales `amount` y `processed_at`, con restricción de ambos ausentes o importe positivo y fecha presente. No cambia datos anteriores ni inventa pagos, fechas o importes históricos. Si una reserva antigua aún vigente no tiene pago, el primer procesamiento crea su registro. Compose aplica la migración al iniciar; para ejecución local usamos `uv run alembic upgrade head` antes de levantar la API.

## Verificación y alcance

CA-01 a CA-09 se cubren con autorización, aprobación/rechazo, persistencia, reintentos, límites temporales, contrato conservado y errores. Las pruebas frontend usan Jest/React Testing Library con HTTP simulado; backend usa Pytest con PostgreSQL real y esquemas aislados. Comprobamos contención real entre solicitudes de pago y el protocolo compartido frente a un escritor de cancelación de prueba, en ambos órdenes. Este último no sustituye el desarrollo ni las pruebas del endpoint de HU-15.

La suite específica incorpora 22 pruebas backend y 21 frontend. Registramos la revisión, comandos y resultados reales en Jira y en el PR. La cancelación sigue en HU-15 y las E2E se reservan para entrega 3.

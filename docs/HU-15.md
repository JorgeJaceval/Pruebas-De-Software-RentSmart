# HU-15 — Cancelar una reserva (REN-15)

Como arrendatario o propietario de un espacio reservado, quiero cancelar antes del inicio para liberar el horario cuando no podrá utilizarse. Fuente: [REN-15](https://rentsmartpsf.atlassian.net/browse/REN-15), CA-01–08.

## Recorrido y decisiones

En `#mis-reservas`, **Cancelar reserva** aparece para pendientes vigentes o pagadas futuras cuando el servidor informa `can_cancel=true`. La confirmación compartida muestra espacio, fecha/horario de Santiago y el reembolso total simulado cuando existe pago aprobado. **Volver sin cancelar** o Escape antes del envío no modifican la reserva. La confirmación gestiona foco y teclado; durante el envío impide duplicados y cierre accidental.

Solo una respuesta válida del servidor cambia la tarjeta a **Cancelada**, la mueve a **Historial** y retira los accesos a pagar/cancelar. El historial conserva inicio descendente y UUID como desempate, también al incorporar una cancelación sin recargar. Mostramos el resultado del pago: aprobado pasa a reembolsado; pendiente/rechazado conserva su estado sin inventar devoluciones. Referencia, importe y fecha del pago existente se conservan.

Actualizar o recargar consulta nuevamente el estado real. No alteramos `as_of` del listado para inventar una nueva hora de consulta completa tras modificar una sola reserva. Ante conflicto, servicio no disponible o fallo de red, mostramos el motivo y ofrecemos volver al panel para actualizar. Un error de red puede llegar después de una transacción confirmada: no anunciamos éxito ni aseguramos que el servidor no cambió; la nueva consulta y la idempotencia permiten recuperarse. Se descartan respuestas después de navegar, cerrar sesión o vencer la sesión.

`can_cancel` orienta la interfaz y no autoriza la operación: la API vuelve a comprobar permisos y tiempo bajo sus bloqueos. No implementamos cancelación desde el resumen individual; el acceso previsto está en Mis reservas y Reservas recibidas.

## Contrato compartido y criterios

`POST /api/reservations/{id}/cancel` requiere sesión y cuerpo `{}`. Devuelve `200` con la reserva cancelada. Conservamos `401` sin sesión, `404` ajena/inexistente, `422` inválida, `409` no elegible y `503` de persistencia. No exponemos la auditoría interna ni datos privados de otras cuentas.

| Criterio | Implementación y verificación |
| --- | --- |
| CA-01 | API autoriza únicamente arrendatario o propietario; administrador ajeno no obtiene privilegio. Pytest de permisos existente. |
| CA-02 | Inicio estrictamente futuro y pendiente no vencida; comprobación del reloj del servidor después de adquirir bloqueos. Límites exactos en Pytest. |
| CA-03 | Confirmación compartida con contrato y aviso de devolución; Jest y E2E desde ambos paneles. |
| CA-04 | Estado, `cancelled_by` y `cancelled_at` guardados; historial conserva contrato y libera intervalo. Auditoría en PostgreSQL mediante Pytest; nueva reserva mediante UI en E2E. |
| CA-05 | Reembolso total simulado del pago aprobado en la misma transacción; pendiente/rechazado sin devolución ficticia. Pytest, Jest y E2E. |
| CA-06 | Repetición devuelve estado guardado, conserva primer autor/fecha y referencia; Pytest y contraste API en E2E. |
| CA-07 | Expirada, finalizada o iniciada recibe conflicto sin cambios; Pytest y presentación de error en Jest. |
| CA-08 | Bloqueo espacio → reserva → pago compartido con pago; carreras reales ya verificadas en Pytest. La suite UI no pretende demostrar concurrencia transaccional. |

La migración `0007` y las pruebas de transacción pertenecen a entrega 2. Este cambio no necesita migración ni cambios backend. No hay dinero real ni integración bancaria.

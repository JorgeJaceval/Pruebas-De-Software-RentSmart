# HU-03 — Publicar un espacio (REN-3)

Como propietario, quiero publicar un espacio con sus características y condiciones para que otras personas puedan encontrarlo y arrendarlo.

Fuente: `Historias de usuario.pdf`, páginas 8–9; rangos comunes de las páginas 3–4 y reglas RN-05/06/07/16/20. Tarea: [REN-3](https://rentsmartpsf.atlassian.net/browse/REN-3). Depende de [HU-02](HU-02.md).

## Comportamiento disponible

Implementamos **Publicar espacio** para cuentas autenticadas. El formulario recibe nombre, descripción, tipo, comuna, ubicación referencial, capacidad, precio por hora, condiciones, fotos y horario diario. Iniciamos el horario en 09:00–18:00 y permitimos editarlo antes de publicar.

Validamos en el formulario y en la API. Recortamos los espacios exteriores de los textos; aceptamos los tres tipos propuestos: sala de reuniones, estudio fotográfico y sala multiuso. Capacidad y precio son enteros; el precio se expresa en CLP por hora. El horario usa horas enteras de un mismo día, con apertura menor que cierre y cierre máximo a las 23:00.

Previsualizamos entre una y tres fotos mediante URLs HTTPS. Si una imagen no carga, mostramos un reemplazo visual. La API valida las URLs sin descargar las fotos ni garantizar la disponibilidad del servidor externo.

Obtenemos el propietario desde la sesión y generamos el UUID y el estado activo en el servidor. Rechazamos campos adicionales como `owner_id`, `id` o `is_active` enviados por el cliente. Durante el envío bloqueamos el formulario y evitamos el doble clic. Ante un error conservamos los datos y permitimos reintentar; confirmamos el éxito únicamente tras recibir la publicación guardada.

Después de publicar mostramos la confirmación y el espacio creado. Recuperamos sus datos desde PostgreSQL al recargar `#espacio/<UUID>`. Esa lectura requiere la cuenta propietaria. Incorporamos la edición con [HU-04](HU-04.md) y la activación/desactivación con [HU-05](HU-05.md). La interfaz de catálogo, el listado completo y la eliminación pertenecen a historias pendientes.

## Validaciones

| Campo | Regla |
| --- | --- |
| Nombre | 5–80 caracteres |
| Descripción | 20–1000 caracteres |
| Tipo | Sala de reuniones, estudio fotográfico o sala multiuso |
| Comuna / ubicación referencial | 2–80 / 5–150 caracteres |
| Capacidad | Entero entre 1 y 100 |
| Precio por hora | Entero entre 500 y 500.000 CLP |
| Condiciones | 10–500 caracteres |
| Fotos | Entre una y tres URLs HTTPS válidas |
| Horario | Enteros: `0 ≤ opening_hour < closing_hour ≤ 23`; valores iniciales 9 y 18 |

## Contrato y persistencia

`POST /api/spaces` requiere `Authorization: Bearer <token>` y recibe `name`, `description`, `category`, `commune`, `location_reference`, `capacity`, `price_per_hour`, `conditions`, `photos`, `opening_hour` y `closing_hour`. Las categorías del contrato son `meeting_room`, `photo_studio` y `multipurpose_room`.

Respondemos `201` con esos datos y `id`, `owner_id`, `is_active` e `is_withdrawn` (falso al publicar, añadido por HU-05). `GET /api/spaces/{id}` recupera el espacio de la cuenta propietaria. Devolvemos `401` sin sesión válida, `403` si otra cuenta intenta consultarlo, `404` si no existe, `422` para datos inválidos y `503` para fallos de persistencia. Los errores de formulario contienen mensajes por campo sin publicar detalles internos.

La migración `0002_create_spaces` agrega `spaces`, la referencia a `users` y las restricciones de datos. Aplicamos la migración sin modificar las cuentas existentes. Las respuestas privadas usan `Cache-Control: no-store`.

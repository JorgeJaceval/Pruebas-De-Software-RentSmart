# HU-02 — Iniciar y cerrar sesión (REN-2)

Como usuario registrado, quiero iniciar y cerrar sesión para acceder a mis funciones y dejar de estar autenticado cuando termine.

Fuente: `Historias de usuario.pdf`, página 8. Tarea: [REN-2](https://rentsmartpsf.atlassian.net/browse/REN-2). Depende de [HU-01](HU-01.md).

## Comportamiento disponible

Implementamos el formulario **Iniciar sesión**, la recuperación del acceso después de recargar y el cierre desde la navegación principal. Normalizamos el correo y verificamos la contraseña exactamente como se ingresó, contra el hash Argon2id almacenado. Un correo inexistente y una contraseña incorrecta producen el mismo mensaje de credenciales inválidas.

Firmamos un token JWT con HS256 y vigencia de 30 minutos por defecto. Incluimos el UUID de la cuenta, la emisión y el vencimiento; no incorporamos contraseña, hash ni rol. En cada petición privada verificamos firma y vigencia y consultamos la cuenta en PostgreSQL. Los permisos administrativos dependen de `is_admin` en la base de datos.

Guardamos únicamente el token y su vencimiento en `sessionStorage`, para conservar el acceso al recargar esa pestaña. Recuperamos los datos de la cuenta desde la API antes de mostrar las vistas privadas. Al vencer o recibir `401`, eliminamos el acceso y solicitamos iniciar sesión. Un fallo de conexión permite volver a verificar sin mostrar contenido privado sin confirmar la sesión.

Al cerrar sesión eliminamos el acceso del cliente y actualizamos la interfaz. Una respuesta pendiente no puede restaurar una sesión que ya cerramos. El token emitido mantiene su vigencia si se copia fuera de ese cliente; seguimos el alcance del criterio CA-04, sin revocación global.

Mostramos **Mis espacios** y **Mis reservas** para cuentas autenticadas y **Administración** para cuentas administrativas. Incorporamos la publicación de espacios con [HU-03](HU-03.md); el listado completo, las demás operaciones de gestión, las reservas y la administración de publicaciones corresponden a historias pendientes. El registro ofrece navegación al inicio de sesión sin autenticar automáticamente.

## Criterios y alcance

| Criterio del PDF | Comportamiento implementado |
| --- | --- |
| CA-01 | Credenciales válidas establecen una sesión limitada y habilitan la navegación privada |
| CA-02 | Correo inexistente y contraseña incorrecta reciben el mismo `401` y mensaje genérico |
| CA-03 | Recarga con sesión vigente recupera la cuenta; vencimiento vuelve a solicitar acceso |
| CA-04 | Cierre elimina el acceso de la pestaña y protege el regreso a vistas privadas |
| CA-05 | Las rutas privadas comprueban cuenta y permisos en el backend |
| CA-06 | Firma, vencimiento y cuenta se verifican; el cliente no decide el rol |
| CA-07 | Enlaces privados visibles; enlace administrativo condicionado al rol del servidor |

## Contrato de API

| Endpoint | Entrada y resultado |
| --- | --- |
| `POST /api/auth/login` | JSON con `email` y `password`; `200` con `access_token`, `token_type`, `expires_at` y `user` |
| `GET /api/auth/me` | `Authorization: Bearer <token>`; `200` con `id`, `name`, `email` e `is_admin` |
| `GET /api/auth/admin-access` | Mismo encabezado; devuelve la cuenta solo si conserva permisos administrativos |

Devolvemos `401` cuando el acceso falta o el token no es válido, `403` cuando la cuenta carece del permiso administrativo y `422` para entradas inválidas o campos adicionales del formulario. Los fallos de persistencia reciben un mensaje controlado. Las respuestas de sesión usan `Cache-Control: no-store` y excluyen contraseñas y hashes.

Configuramos `AUTH_SECRET_KEY` en el servidor con al menos 32 caracteres y `AUTH_TOKEN_MINUTES` entre 1 y 1440. La clave no se incorpora al frontend ni se versiona. Documentamos la preparación de ambos archivos `.env` en el [README](../README.md).

## Verificación

Probamos la autenticación y los permisos con Pytest, FastAPI `TestClient`, las migraciones reales y esquemas aislados de PostgreSQL. Probamos formulario, recuperación, navegación, expiración y cierre con Jest/React Testing Library y HTTP simulado. Registramos los resultados y la revisión ejecutada en **Testing** de [REN-2](https://rentsmartpsf.atlassian.net/browse/REN-2) y en el PR de la historia.

La recuperación tras recargar se representa remontando la aplicación en las pruebas de interfaz. Reservamos las E2E para la entrega 3 y mantenemos separados estos resultados de la aceptación de usuario.
